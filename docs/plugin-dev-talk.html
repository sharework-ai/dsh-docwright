功能概览

docwright：把"AI 生成文档"变成受控闭环

docwright 是 deepseek-harness（dsh）的文档生成与校验插件：AI 生成结构化 JSON 文档 → 按 pack 的 schema 与领域规则强制校验 → 不合格把问题清单喂回模型重写，直到全绿或明确失败； 每份文档随盘附带机器可读的验证回执（receipt），任何人可离线复验。

核心理念一 · JSON 为中心

文档以结构化 JSON 表示，配合 JSON Schema——所有文档可机器校验，"看起来对"不再等于"真的对"。

核心理念二 · 场景化配套

按工作场景组合"生成方法 + 检查方法"：pack = schema + 规则 + prompt + 模板的数据包，可插拔。

与 instructor / BAML / Guardrails 等结构化输出框架的差异：它们只判断结构对不对（字段齐不齐、类型对不对）， 判断不了内容合不合格——"功能描述写满 80 字""名称禁用泛化词""估算总和落在业务区间"这类标准因文档类型而异。 docwright 的差异化：合格标准可插拔（pack）+ 校验结论可复验（receipt）。

一句话分工：换文档类型 = 新写一个 pack 目录，插件零改动；改闭环 / 校验 / 回执行为 = 改插件。

研发背景

文档生成的三个痛点

工作中需要让 AI 大量生成文档，但生成过程缺少 harness 护栏，质量不可控：

1

非结构化内容

  • AI 直出 Markdown / Word 自由文本
  • 质量是黑箱——无法机器校验
  • "看起来对" ≠ "真的对"，评审全靠人肉通读
2

没有统一的规范

  • "什么算合格"散落在人脑、聊天记录、模板批注里
  • 同一个标准，两个人执行出两种结果
  • 规范本身没有载体、没有版本
3

要求随时变化

  • 文档标准、版式、预算口径频繁调整
  • 标准硬编码在 prompt / 代码里
  • 每次调整都是一次开发
研发背景 · 对症下药

三个支柱，分别对症

治痛点 2 · 3

领域规则包 pack

合格标准数据化：schema + 规则 + prompt + 模板打进可插拔数据包。
换文档类型不换代码，标准变化不进开发流程。

治痛点 1

闭环修复 repair loop

生成 → 校验 → Issue 喂回重写 → 全绿或明确失败。
护栏是强制的，不是 prompt 里的"请自觉遵守"。

治信任问题

可复验回执 receipt

"全绿"从一次过程变成一件产物：机器可读、离线可复验、可追溯当时规则。

边界即架构：插件 = 引擎（闭环、校验执行、回执、路径安全），pack = 内容（一类文档的全部领域知识）。 领域概念（COSMIC、CFP……）禁止进入插件代码。

dsh 插件开发

dsh：一切皆插件的 agent harness

  • dsh 基于 vendored Cordis（插件框架）：运行中的 dsh 是一棵由有序配置层组合出的插件树
  • 无特权核心：模型适配器（ctx.llm）、工具注册表（ctx.tools）、session 日志、甚至 agent loop 本身都是插件，均可被配置替换
  • 扩展方式 = 在旁边挂一个插件：Plugins, not loop changes——新行为走扩展点，不改 agent-loop

Cordis 五要点

  • 插件 = Service 实现
  • Context = 服务仓库（服务认领稳定的 ctx.<key>）
  • inject 声明依赖——以服务需求表达加载顺序
  • 类型化事件通信（ctx.on）
  • 注册皆可逆效果（返回 disposer）

对插件作者意味着什么

  • 你写的插件与官方内置插件完全平级——docwright 没有任何后门
  • 能力通过 seam（服务接口）消费：换实现 = 换一行配置
  • 配置错误在装载期响亮失败（misconfiguration fails loud），不带病进会话
  • 配置编辑支持热替换（HMR）：卸载旧实例按 disposer 逆序清理，装载新实例

dsh 插件开发

插件契约：name / inject / apply(ctx)

export const name = 'docwright' // 诊断用 export const inject = ['tools', 'llm'] // 依赖的服务；未就绪则等待，运行中消失 → 自动 dispose export function apply(ctx: Context, config: Config) { const packs = loadPacks(config.packsDir) // 加载期校验：坏 manifest → apply 抛错 → 插件启动失败（fail loud） for (const pack of packs) ctx.tools.register(defineTool(makeTool(pack))) // 每条注册返回 disposer；卸载 / HMR 按序 unwind }

Config：声明即校验

  • TS 接口 + Schemastery schema（Standard Schema）成对导出
  • apply 收到的是校验并补默认值后的配置
  • 部署间可能不同的值必须是 Config 字段——禁止硬编码 tunable

注册皆效果（Registrations are effects）

  • 一切注册走 ctx.effect() / ctx.on()，均返回 disposer
  • 插件卸载 / 热替换时自动逆序清理，零残留
  • registry 需配 HMR-safety 测试（dispose 后验证清理）

加载期 fail loud

  • schemastery 装载期校验 config
  • 引用的外部资源缺失 → 最早可解析点失败
  • docwright：坏 pack / 缺技能 guide / 默认语言不被支持 → 启动即报错
dsh 插件开发

工具如何进入 agent loop

ctx.tools.register(defineTool({ name: 'doc_generate', description: '闭环生成文档…先用 doc_packs 查看可用 pack', // ← 模型的"说明书"，静态文案（拉式渐进披露） parameters: { /* schemastery DSL：参数 schema，模型可见 */ }, output: { schema: /* 返回值 schema */, render: /* 给模型看的渲染 */ }, execute: async (args, signal) => docService.generate(args), }))

① 模型可见投影

registry 的 schemas() 只白名单投影 name / description / parameters 组成 ToolSchema[]；execute / render 等永不进请求。system-prompt 服务组装 PromptAssembly，loop 每步携带；集合变化经 tools/change 事件下一 step 生效。

② 模型发起 tool call

模型从投影出的工具清单中选择并传参——工具 description 就是模型的能力地图。docwright 把"先调 doc_packs"的邀请写死在 description 里，不随 pack 集合膨胀。

③ 执行与回填

返回值经 output.render 变 ContentBlock 回给模型；同时写入 durable session 日志——模型可见 ⟺ 日志可重建。

pre-execute 权限 waterfall→ ToolGuard→ execute 工具体→ post-execute 审改→ session 日志

PART 3 · 关键设计

docwright 的五个关键设计

这些设计回答同一个问题：怎么让"AI 生成文档"的每个环节都可校验、可追溯、可治理。
① pack：内容与引擎分离 ② 闭环修复与打分 ③ 回执与 checksum ④ 参数治理 ⑤ 链契约与扇出
关键设计 ①

pack：内容与引擎分离换文档类型 = 新 pack 目录，插件零改动

packs/<name>/ — 七件套
manifest.json # 元数据·链消费·参数声明 schema.json # JSON Schema：文档长什么样 rules/<lang>.json # 声明式规则（四族） rules/functions.js # 跨字段函数规则（可选） prompts/<lang>.md # 生成 prompt，{{materials}} 槽位 templates/<lang>.hbs # Markdown 渲染模板 samples/golden.json # 全绿母本 + 变异测试输入

声明式四族：minLength / maxLength / forbiddenKeywords / pattern； 规则边界可引用参数（{"param":"..."}，含 pattern 正则参数）。

  • 声明即白名单：manifest.params 未声明的参数名谁都不能调
  • 每条规则必须带 suggestion——修复 prompt 的质量不随 pack 作者漂移（加载期强制）
  • golden 必须全绿，且每个规则族配"故意损坏"变异测试——抓不住损坏样本的 checker 是摆设
  • 改规则语义必须升 version：旧产物回执被 staleness 识别为过期
  • 造 pack 也是插件能力：运行时技能 docwright-pack-authoring（九阶段 playbook）+ pack:check（真实装载门 + golden 全绿验证）——AI 教 AI 造 pack
关键设计 ②

闭环修复：校验是强制的护栏生成 → 校验 → 修复，直到全绿或明确失败

预算预检
token 估算超限响亮报错→ 模型调用
ctx.llm 路由 · 失败重试 1 次→ 解析
剥围栏提取 JSON
解析失败也是 Issue→ 校验
ajv + 声明式 + 函数规则
归一为统一 Issue 格式→ 判定
全绿 = 0 条 ERROR
warning / info 不拦截⇤ 未全绿 → 下一轮

统一 Issue 格式 = 闭环的粘合剂

{ ruleId, severity, jsonPath,
  message, snapshot, suggestion }

修复 prompt、回执、报告只消费这一种格式；修复指令 = "只修列出的问题，输出完整 JSON"。

失败语义：绝不静默采用

  • 迭代耗尽 → 工具抛错（fail loud）
  • 草稿 + 红回执留在磁盘，供人工救援
  • 落盘三件套均为 tmp+rename 原子写，产物先于回执——崩溃只会留下可读草稿，不会留下孤儿回执
关键设计 ②

打分机制与收敛检测分数决定"何时放弃"，全绿判定始终是 0 ERROR

内置默认评分

100 − 10×error − 3×warning − 1×info

clamp 到 0-100；权重可配（Config）。e2e 实测多轮轨迹与该公式精确吻合。

pack 自定义评分

score(artifact, issues) => 0-100

领域自定义收敛度量（越高越好）；越界 / 崩溃 fail loud。缺省自动落到内置公式。

分数的用途

收敛检测，不是质量认证

质量认证 = 0 ERROR + 回执；分数只服务于"这一轮值不值得继续烧 token"。

  • 三层提前终止（Config oscillation 可调）：连续 K 轮不超过历史最优 → stagnation；连续 D 轮严格下降 → decline;指纹兜底（连续 3 轮 Issue 指纹相同）→ fingerprint-repeat
  • 终止可审计：终止原因 + 每轮评分与 promptHash 写进回执——收敛过程离线可复盘
  • 轮数解析序：maxRounds 参数 > pack 默认 > Config 默认（5），一律被 maxRoundsCeiling（10，宿主运维持有）钳制
关键设计 ③

回执与 checksum 机制"全绿"从过程变成产物

字段语义
artifactHash产物 canonical JSON（键排序、无空白）的 sha256——hash 把合格证绑定到具体内容版本，改一个字符即失配
schemaHash / rulesetSnapshotschema 哈希 + 声明式规则全文 + functions.js 源码哈希——pack 升级后，历史回执仍能解释"当时依据什么标准"
upstreamHashes链式锚点：每个上游的 pack / packVersion / artifactHash——下游引用的上游当前内容一定绿过
rounds[] / params / terminationReason每轮 issue 数·评分·promptHash；as-run 参数（复验按它重放）；红回执的终止原因

防篡改语义

生成与复验共用同一个回执构造器（永不漂移）；tamper-evident 而非 tamper-proof：误改必红，蓄意伪造产物+回执不可防。

seal 回签：第二个发证渠道

绿校验把新回执写入 sidecar——发证从"只有生产线"扩展为"生产线 + 质检站"；人工 / 外部编辑的产物过校验即重新入链；红校验绝不触碰 sidecar。

版本门与复用

packVersionStale：绿回执只证明旧规则 → 提示重生成。复用预检：同 pack + 绿回执 + hash + 素材清单 + 上游锚点 + 参数全对齐 → reused:true 零 LLM。

关键设计 ④

参数治理：层级与解析序参数是用户意图的正道，不是散落在素材里的散文

层级谁拥有 / 载体
插件 Config部署运维 · cordis.yml
pack manifestpack 作者 · 声明即白名单 + 默认值 + 门控属性
调用参数用户·agent · 单次调用，写进回执沿链继承
引擎派生如 topicNo——只能改其来源（pattern），不能关闭派生
  • 属性全集：type / default / required / confirm / overridable / extractable / min / max / enum
  • 装载期不变量：overridable ⇒ confirm（可调基线必过人）；被规则引用的参数禁 overridable
  • 参数划分：共享参数（CFP 预算族、moduleLevels）链头声明一次沿链继承；pack 本地参数各自声明。继承声明不填 default——写了只是误导性死数据
解析序：显式 params > 上游回执继承 > 抽取值（引文机检）> 声明默认 > required 缺失即 fail loud。
对话中用户意图由 agent 转译为显式 params；materials 散文默认无权配置 pack——防止素材内容静默改写配置。
关键设计 ④

确认门：改参数必过人执行前无人核对生效参数 = 不可接受

# 显式改参或 confirm 参数未经上游确认时： doc_generate(pack: "cosmic-plan", params: { cfpTotal: {value: 100, downFactor: 0.9, upFactor: 1.2} }) → pendingConfirmation # 结构化参数表，零 LLM 成本，不执行 ├ cfpTotal value=100 [0.9, 1.2] source=explicit 漂移预判: 将按新预算生成 └ cfpPerFunc value=30 [15, 45] source=pack-default doc_generate(…, confirm: true) # 用户确认后重发 → 执行
  • 沿链继承不再立门：共享参数链头声明一次，as-run 写进上游回执，下游继承——全链用户交互恰一次，位置在链头
  • 来源标注：pack 默认 / 显式传入 / 上游继承 / 抽取引文——参数表上每个值都有出处
  • 档位 confirmPolicy：none（headless/CI）/ standard（默认）/ strict（每阶段都过）
  • 审计兜底：谁批了什么，session log 可完整重建（模型可见 ⟺ 日志可重建）；模型未转呈就自答 confirm:true 属调用方违规，凭日志追责
关键设计 ④

Mind the gap：生成语义与校验语义分家

进 prompt

只有 value 是生成目标

参数对象投影 {value} 渲染进 <effective-params>——模型会把上下文中出现的数值当作写作目标贴合。

留在规则

区间端点是校验容差

min / max / downFactor / upFactor 只活在规则与回执，经修复回路的 Issue 消息到达模型——不进生成上下文。

真实教训：把校验带 cfpPerFunc {30, 10, 100} 整个写进 prompt——带太宽时违约值合法通过（1×70 的单功能规划全绿通过）； 带收紧后模型又压缩估算凑带宽而不是拆分模块。生成语义与校验语义混在一起，两头都输。
判断标准一句话：这个数描述"文档应该长什么样"（进上下文），还是"离目标多远必须打回"（留在规则）？
若 min/max 本身就是生成语义（"单功能不低于 10"），把它升级为独立参数的 value（cfpMin / cfpMax）。
关键设计 ④

素材参数读取：引文机检的出处链doc_extract_params——从模型不可见的推理变成可机检的证据

doc_extract_params(pack: "cosmic-plan", materials: ["req.md"], extractions: { cfpTotal: { value: 70, quote: "the expected CFPs is 70" } }) → 引擎机检：quote 必须是素材逐字子串（空白归一后包含）+ 值过参数 spec → 通过才入解析第三档

notFound 是一等结果

  • 引文不在素材中 / 模型未提出 / 素材没写 → 记 notFound，不报错、不代答
  • required 参数 notFound → 花费生成成本之前拦截，请用户给值或认可建议值
  • 素材缺值被模型代答必须防止，不以模型能力提升为豁免理由

缓存与复验

  • 抽取结果落 <pack>.extracted.json（pack 版本、素材 anchors、逐参数记录）——是缓存，不是契约
  • 生成前对当次素材重验每条引文：素材变了 / 引文失配 / spec 收紧 → 丢弃落回下一档
  • 抽取发生在链头之前、扇出之前——一次抽取保护整条链（值沿回执继承）

确认表上的出处列

  • source: extracted 行附 quote + 引文位置——抽取值以引文自证
  • 建议值（suggestion）过同一 spec 校验，但永不自动生效——用户认可的唯一通道是显式 params
关键设计 ⑤

链契约与扇出（1:N:N:N）覆盖是集合性质，归链级账目，不塞进单产物规则引擎

  • upstream 六项校验：可读 JSON / 有 sidecar 回执 / 回执绿 / hash 未变 / pack 类型匹配 consumes / 版本策略（strict 拒绝 · warn 放行并告警）；其余已装 pack 的绿产物可作 rider 随行入 prompt（如按需携带项目 context）
  • targetIndex 必填无默认：缺失即 fail loud 并列出全部候选——历史上"静默选 index 1"曾让 9 个功能只生成 1 份且校验全绿
  • 引擎命名权：per-function 产物 <PREFIX>-<topicNo>-<NN> 由引擎命名，显式传 artifactName 报错——同名覆盖在机制上不可能发生，重生成幂等
  • doc_chain_status 账目：覆盖矩阵（每个 plan 功能在 req/func/tech 层是否绿）+ orphaned 清单（funcId 不属于任何 plan 功能的产物）——agent 收工呈现前必须对账
  • 跨出处链实证（2026-11-03 e2e 八步全绿）：packsDir 里的外部 pack 消费内置 cosmic 链——引擎零改动：参数沿回执继承、确认门跨出处只立一次、chain-status 自动入册
参数漂移：paramDriftPolicy —— regenerate（默认，质量优先）/ revalidate（确定性重验上游，零 LLM）。 下游显式传参与上游回执不一致 = 改参数 → 重新立门。

研发历程 · 复盘

三条复盘与工程实践

1

真实会话是最好的设计输入

参数治理四缺口全部来自一次真实 web 会话——"9 个功能只生成 1 份且校验全绿"：护栏对"没发生的事"不设防，覆盖必须靠集合级账目补上。

2

测试要穿过宿主运行时

"测试直调 execute() 绕过 dsh 运行时校验"曾让 confirm-gate undefined bug 漏网（lossless-JSON 快照拒绝 undefined）——单测绿 ≠ 真实宿主绿。

3

文档纪律是研发效率

规格零历史（推演进 git，正文只写现状）、one home per fact、设计文档 PROPOSED → implemented 状态机——13 份设计文档是决策资产，不是流水账。

质量门：每文件 100% 行/函数/语句覆盖 · 变异测试证明护栏非摆设 · 闭环用确定性策略测试（LLM seam 注入脚本）· smoke:host 无 key 预发布冒烟 · 真实模型只进 e2e。
dsh 约定落地：no hardcoded tunables（全部旋钮是 Config 字段）· 模型可见 ⟺ 日志可重建（promptHash 入回执）。
总结

三个可复用的设计原则

1

合格标准数据化

标准是数据（pack）不是代码——变化不进开发流程；声明即白名单，版本门让历史产物自动识别为新旧标准之下。

2

校验结论产物化

"合格"不是过程是产物（receipt）——可复验、可追溯当时规则、可 seal 续链；hash 把合格证绑定到具体内容版本。

3

治理机制内建于工具

确认门 / 覆盖账目 / 防篡改 / 出处链都长在工具语义里——靠模型自觉的护栏等于没有护栏。

  • 展望：草稿续修（红回执断点续修）· MCP 包装（宿主无关分发）· pack npm 分发 · as-run 参数值记录 · 更多场景 pack
一句话收尾：让 AI 生成文档从"碰运气"变成"可验证的工程"。
