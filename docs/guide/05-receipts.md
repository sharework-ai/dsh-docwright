# 5. 回执与复用

## 回执是什么

回执（receipt）是一份机器可读的校验结论文件，随产物落盘为 `<产物名>.receipt.json`（sidecar），同时内联在 `doc_generate` 与 `doc_validate` 的返回值中。它回答三个问题：这份产物依据哪套规则被判为合格、生成过程经历了什么、链上锚定了哪些上游。

回执记录的主要内容（语义层面）：

| 记录 | 用途 |
|---|---|
| pack 名与版本、语言、模型标识 | 说明产物出自哪套规则、哪个生成环境 |
| 产物 canonical JSON 的 sha256 | 把合格结论绑定到具体内容版本；内容一变，结论即失配 |
| 规则集快照 | pack 升级后，历史回执仍能解释当时的判定依据 |
| 闭环轨迹（轮数、每轮 issue 计数与评分、终止原因） | 修复过程可审计；`terminationReason` 说明终止缘由 |
| 生效参数（as-run） | 当时用什么参数生成；`doc_validate` 默认按它复验 |
| 上游锚点（链式 pack） | 记录每个上游的 pack、版本与内容哈希，下游据此验证上游未被改动 |

回执是防误改而非防伪造：无签名，误改产物或回执会在复验时暴露；蓄意同时伪造产物与回执不在防御范围内。

## 拿回执做什么

### 离线复核

任何人拿到产物与回执，可用 `doc_validate` 重跑同一规则集复核结论，不需要模型参与。返回值中的 `hashMatches` 报告产物是否与回执一致（`false` 即生成后被改过），`packVersionStale` 报告回执是否出自旧版 pack（`true` 即绿色结论证明的是旧规则，应重新生成）。

### 链上准入

链式 pack（声明 `consumes`）在生成与复验时对每个 `upstream` 引用做一组检查：文件可读且为合法 JSON、存在回执、回执为合格、回执记录的哈希与当前内容一致、pack 类型在消费清单内、pack 版本符合 `upstreamVersionPolicy`（`strict` 拒绝版本不符的上游，`warn` 放行并附 `upstreamWarnings`）。任一不过即报错。结论：**不合格产物永远流不进下游**。

不在消费清单内、但属于已安装 pack 的合格产物可以作为随行上游（rider）注入生成上下文，例如 req 阶段按需携带项目 context；但至少要有一个清单内上游。

### 参数与配置的复现

回执记录 as-run 参数，`doc_validate` 默认按它复验，即按生成当时采用的标准检验产物；显式传 `params` 可做 what-if 检查。

## 封章（sealing）

`doc_validate` 对当前内容完整校验，合格时把新回执写入 sidecar，返回值带 `sealed: true`。这为人工修改的产物提供了重新入链的通道：

1. 生成后有人手工修改了产物，哈希与回执失配，链上校验拒绝它；
2. 用 `doc_validate` 复验，若修改后的内容仍通过全部规则，回执按新内容重新签发（`sealed: true`），产物重新可用于下游；
3. 复验不合格则不触碰 sidecar，改坏的内容拿不到合格证明。

发证渠道因此有两个：生成线（`doc_generate`）与质检站（`doc_validate`），两者使用同一套回执构造逻辑，结论不会漂移。

## 复用预检（reuse）

`doc_generate` 在生成前做复用检查：若产物根下已存在同 pack、同版本、内容哈希一致、素材清单一致、（链式 pack）上游锚点一致、寻址产物名一致的合格产物，则直接返回它，返回值带 `reused: true`，零模型调用。任一不一致，或调用带 `force: true`，走正常生成。

实际效果：重复调用同一 `doc_generate` 不重复计费；素材被改动、上游重新生成、参数变化中任何一项发生，都会触发重建。人工封章过的产物（内容变了）不会被复用结果覆盖——`force: true` 或输入变化导致重建时，以当前磁盘上的输入为准。

## pack 版本过时（packVersionStale）

回执记录生成时的 pack 版本。`doc_validate` 发现回执出自与当前安装版本不同的 pack 时返回 `packVersionStale: true`：此时即使复验合格，绿色结论证明的也是旧规则，正确做法是重新生成。无版本记录的旧回执同样视为过时。这条检查配合 `upstreamVersionPolicy` 保证链上每一环都是当前规则的产物。
